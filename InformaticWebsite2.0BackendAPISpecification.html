Informatic Website 2.0 – Backend API Specification

Version 1.1 · Base path /api/v1 · Audience: backend developers

1. Overview

Template-driven website plus admin panel. The frontend ships pre-built templates for every page. The admin picks the active template per page and manages content. The backend stores:

  • Active template ID per page (layouts)
  • Content records (services, portfolio, blog, events, team, testimonials, gallery, careers, FAQs, legal pages)
  • Navigation, footer and home-section config
  • SEO and image ALT data per page
  • Contact inquiries and admin accounts

Two API surfaces:

  • Public /api/v1/public/*: no auth, read-only, cacheable. Only exception: contact inquiry POST.
  • Admin /api/v1/admin/*: JWT required, full write access.

Endpoints marked NEW were missing from the original scope but are required for the system to work. Everything else comes straight from the original scope.

Base URL https://api.yourdomain.com/api/v1 (local dev: http://localhost:5000/api/v1). Admin requests send Authorization: Bearer <JWT_TOKEN> and Content-Type: application/json. Field names and response shapes in the module sections follow the frontend reference guide; the frontend already consumes them, so treat them as the contract.

2. Conventions

2.1 Authentication

  • Admin endpoints need Authorization: Bearer <accessToken>.
  • Missing or invalid token: 401. Valid token but insufficient role: 403.
  • Public endpoints never require a token.

2.2 Response envelope

Success:

// read (lists add total)
{ "success": true, "data": [ ], "total": 6 }

// write
{ "success": true, "message": "Topbar layout updated to layout2" }

Error:

{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "Invalid input", "details": [ { "field": "slug", "message": "Already exists" } ] } }

List endpoints return data as an array plus total (count of all matching records). Layout and settings writes return a message; create and update calls also return the saved record in data.

Small collections (team, testimonials, FAQs, gallery albums) may return everything without pagination if limit is omitted.

2.5 Content rules

  • id: integer or string (frontend samples use integers such as 1). :id in admin routes is always the id. :slug in public routes is always the slug.
  • slug: lowercase, hyphenated, unique per module. Auto-generate from title if omitted. Return 409 on duplicate.
  • Public GET returns only records with isPublished: true (blog and events use status: published).
  • order: integer for manual ordering. Lower comes first.
  • All records carry createdAt and updatedAt (ISO 8601 UTC).
  • Rich text fields (fullDescription, content, etc.) are HTML. Sanitize server-side on write (allow-list tags) to prevent stored XSS.
  • Images are stored as URLs returned by the upload endpoint (section 3.3). Never accept base64 blobs inside JSON.

2.6 Caching

Public GETs should send Cache-Control: public, max-age=60 and an ETag. Admin GETs send no-store.

Login request and response:

{ "email": "admin@example.com", "password": "..." }

{ "data": { "accessToken": "...", "refreshToken": "...", "expiresIn": 900, "admin": { "id": 1, "name": "", "email": "", "phone": "", "bio": "", "avatar": "", "role": "super_admin" } } }

Rules:

  • Access token (JWT) lifetime 15 minutes; refresh token 7 days, rotated on use, stored hashed.
  • Passwords hashed with bcrypt or argon2. Never return the hash.
  • Wrong email or password returns the same 401 message (do not reveal which was wrong).
  • Lock the account for 15 minutes after 5 failed attempts.
  • change-password body: { "currentPassword": "", "newPassword": "" }. Minimum 8 characters, must differ from the current one. Invalidate other sessions after change.
  • profile body: { "name": "", "email": "", "phone": "", "bio": "", "avatar": "url" }. Email must stay unique (409).
  • Logout revokes the refresh token.
  • Roles: super_admin (everything, including footer custom code) and editor (content only). One role is acceptable for v1.

The reference examples use the demo login admin@example.com / admin123: seed that account only in development and force a password change before production.3. Shared Resources

For *-detail pages, the SEO record is the page-level default. Each content record (service, case study, post, event) may also carry its own optional seo object with the same fields. Public detail responses return the record's seo if set, else the page default.

GET /public/footer returns { layoutId, cta, grid, links, customCode }. Only links with enabled: true are returned publicly. customCode carries an enabled flag; when false the frontend injects nothing. Default customCode: { enabled: false, html: "", css: "", js: "" }.

Security: custom JS/HTML is injected on the public site by design, so it is a stored-XSS vector if an admin account is compromised. Restrict custom-code to a super-admin role and log every change. Do not sanitize it away (that would break the feature); keep it admin-only.

6. Open Items to Confirm with Frontend

  1. Portfolio catalog count. Scope says 8 templates but lists 7. Confirm the count; the layout validator needs the exact range.
  2. Layout ID format. Spec assumes layoutN for every key. Confirm the frontend uses the same strings.
  3. Home page content. Hero copy, CTA banner text, stats numbers (stats), client logos (clients) and About content are toggleable sections but have no content endpoints. Either add a home-content resource or confirm they are hardcoded.
  4. Image ALT tags. Handled inside the SEO imageAltMap plus page-level image slot IDs. Confirm this is enough.
  5. Newsletter. Footer template layout2 shows a newsletter form. If it should submit, add POST /public/newsletter/subscribe.
  6. Career applications. Currently only job listings. If candidates apply on-site, add an applications endpoint with resume upload.
  7. Roles. Confirm whether one admin role is enough for v1.
  8. Draft preview. Confirm whether admins need to preview unpublished content on the public site (would need a signed preview token).
  9. Module count. The dashboard sample says 19 modules and 98 templates; the scope lists 18 modules. Confirm which is right.
  10. Missing detail in the reference. Careers, FAQs, gallery writes, navbar/footer reset and the Module 13 to 16 payloads have no samples there; the shapes in this doc are proposals.
  11. IDs. Samples use integer IDs. Confirm the DB key type before building (slug stays the public key either way).
  12. Services techStack. In the original scope but not in the frontend contract; confirm whether to keep it.
